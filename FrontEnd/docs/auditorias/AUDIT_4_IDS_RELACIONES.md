## Qué está bien (para no romperlo después)

- **El anti-patrón "resolver proveedor por nombre" ya se erradicó explícitamente donde existía.** `InventoryItem.supplierId: Supplier['id']` (`inventory.types.ts:55`) reemplazó un campo `supplier: string` anterior (comentario explícito en el propio código, E3/Opción A ya implementada) y `PurchaseSuggestion.productId: InventoryItem['id']` (`inventory.types.ts:108`) se agregó específicamente para que "Generar OC" pueda resolver el proveedor real — el propio campo `supplierName` (línea 114) está comentado como "SOLO de exhibición, nunca se usa para resolver el proveedor real". `TabPurchases.tsx:44-59` es el ejemplo de código real que cumple esto al pie de la letra: busca el producto por `suggestion.productId`, después el proveedor por `product.supplierId`, y si no hay proveedor válido **rechaza la operación con un mensaje claro** en vez de inventar o adivinar un `supplierId` a partir del texto de `supplierName`.
- **`Delivery.orderId: Order['id']` (`logistics.types.ts:12`) es una referencia tipada real entre dos módulos distintos**, correctamente resuelta vía import de solo-tipo (`import type { Order } from './order.types'`) sin crear un ciclo de imports en runtime — mismo patrón que `PurchaseOrder.supplierId`/`PurchaseOrderLine.productId`. Es la prueba de que el proyecto ya sabe modelar esto bien cuando se hace a propósito; el problema del hallazgo #1 es que a `Client` nunca se le aplicó el mismo tratamiento.
- **`PurchaseOrdersQueryFilters.supplierId` (`purchaseOrder.types.ts:76`) filtra por ID exacto, nunca por texto libre** — el comentario del propio archivo (líneas 66-70) explica por qué a propósito: Compras no conoce el nombre del proveedor (vive en Suppliers), así que buscarlo por nombre implicaría importar internals de otro módulo; el selector arma la lista de proveedores vía `fetchSuppliers()` (el punto de entrada público) y pasa el id elegido.
- **Ningún `find`/comparación por nombre para resolver una relación de negocio** se encontró en todo el grep de `src/` (patrón `find(x => x.name === ...)`/`x.clientName === ...`/`x.supplierName === ...` contra otra colección): 0 resultados. El problema real (hallazgo #1) no es "se resuelve mal por nombre", es "no se resuelve en absoluto" — dato distinto y importante para no proponer la solución equivocada (no hace falta "arreglar un join por nombre", hace falta agregar el campo de relación que nunca existió).
- **`ClientAccount.id`/`OverdueClientRow.clientId` ya siguen la convención correcta** (`client.types.ts:130`, `ClientOverdueTable.tsx:199` usa `row.clientId` como `keyExtractor`, no `clientName`) — es el ejemplo a replicar cuando se resuelva el hallazgo #1.

## Preguntas abiertas para Leandro

1. **¿`Order`/`Delivery`/`CashTransaction` deben ganar un `clientId: ClientAccount['id']` real, y quién lo asigna?** Hoy `CreateOrderModal` no ofrece ningún buscador de clientes existentes — el campo es un `<input>` de texto libre. Si se agrega la relación, hace falta decidir si el alta de un pedido exige seleccionar un cliente ya existente (bloqueando el alta de clientes ad-hoc "sobre la marcha") o si se permite crear cliente y pedido en el mismo flujo. Esto afecta directamente el diseño de ADR-001 (Tanda 8, entregas) porque una entrega sin `clientId` no puede mostrar el historial de entregas de ESE cliente.
2. **¿Vale la pena modelar "vendedor" como un `UserAccount` real** (ya existe `SystemRole = 'Vendedor'` en `settings.types.ts`) en vez de `sellerName: string` libre, para poder eventualmente filtrar pedidos/comisiones por vendedor real del sistema? No es parte de ninguna tanda del prompt maestro hoy, pero es la misma familia de problema que el hallazgo #1 y convendría decidirlo junto.
3. **¿El campo `entity`/`linkedVoucher` de `CashTransaction`** (texto libre para "Cliente o Proveedor" y "Nro de factura/remito asociado") **debe convertirse en una relación tipada** (`clientId | supplierId` discriminado, y una referencia real a `ClientInvoiceTransaction['id']`/`PurchaseOrder['id']`) o se acepta que Caja siga siendo un registro de texto libre por ser, en esencia, un libro diario donde no todos los movimientos tienen una entidad de sistema del otro lado (ej. "retiro", "gasto" sin proveedor real)? Esto conviene resolverlo antes de intentar cualquier conciliación automática entre Caja y Cuentas Corrientes de Clientes/Proveedores.
