## Qué está bien (para no romperlo después)

- **Existe un patrón local-first correcto y ya se usa en la mayoría de los lugares que generan una fecha-sin-hora**: `toISODateString`/`computeDateRangeForPreset` (`dateRangePresets.ts:36-70`) construye el string `yyyy-MM-dd` con `getFullYear()`/`getMonth()`/`getDate()` (hora local del navegador), nunca vía `toISOString()`. Es el patrón correcto — el hallazgo #1 es exactamente el único lugar del proyecto que no lo sigue pese a que el helper ya existe y está importado en otros módulos (`ExportButton.tsx`).
- **El filtro de rango de fechas (`DateRangeQueryFilters`, `isWithinDateRange`) compara SIEMPRE por string `yyyy-MM-dd`** (`clients.service.ts:212-217`, `.slice(0, 10)` + comparación lexicográfica), nunca instancia un objeto `Date` para la comparación de rango — es inmune por diseño a cualquier problema de zona horaria en ese punto específico, y es el patrón que debería generalizarse a los hallazgos #2/#3.
- **Los campos de fecha de dominio son consistentemente `string` (ISO), nunca `Date` instanciado ni timestamp numérico**, en los 9 tipos de `shared/types/*.types.ts` revisados (`date`, `dueDate`, `expirationDate`, `createdAt`, `timestamp` — todos `string`). Esto es correcto para tipos que cruzan la futura frontera JSON con un backend real: un `Date` de JS no serializa de forma portable, un ISO string sí.
- **`dueDate` en el mock de clientes se genera con hora fija (`10:00` local) antes de convertir a ISO** (`clients.data.ts:43-47`), documentado explícitamente en el propio comentario del archivo como relativo a "hoy" para que los tramos de aging sigan siendo válidos sin importar cuándo se ejecute la app — buena práctica de datos de prueba, independiente del hallazgo #3 (que es sobre cómo se COMPARA esa fecha, no cómo se generó).
- **El cache de snapshot de morosos invalida por día calendario, no solo por referencia de store** (`currentDayKey`/`getOverdueSnapshot`, `clients.service.ts:492-515`) — comentario explícito reconociendo el riesgo de que una sesión abierta cruce la medianoche y siga mostrando el aging de ayer; usa `toDateString()` (local) como clave, exactamente el criterio correcto para ese problema puntual (que es distinto del hallazgo #3, sobre el corte de hora dentro del cálculo de `daysOverdue` en sí).
- **No hay ningún caso de fecha guardada como timestamp numérico ambiguo** (epoch sin unidad clara) salvo `subscription.service.ts:34` (`new Date(year, month - 1, day).getTime()`), que es un uso interno para ordenar/comparar períodos ya parseados de componentes numéricos explícitos (no ambiguo, no depende de parseo de string).
